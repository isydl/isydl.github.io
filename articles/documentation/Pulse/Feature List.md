### 模块 1：用户认证与权限管理（Auth & RBAC）

_这是系统的“大门”，没有它，所有角色都是乱的。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                                  |
| :--------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **三角色隔离**：普通用户（只看自己的）、客服/担当（看全量但不可删）、管理员（全量+可删+可管人）。<br>2. **数据行级权限**：普通用户查列表时，SQL必须强制带 `WHERE user_id = ?`，不能靠前端传参。<br>3. **操作级权限**：比如“删除按钮”只对管理员可见，“状态流转按钮”只对当前处理人可见。 |
| **核心技术点（Java技术栈）** | 1. **Spring Security** 或 **Sa-Token**（推荐，上手快）做拦截器。<br>2. **JWT（Json Web Token）** 做无状态登录（或 Session 保持）。<br>3. **自定义注解**（如 `@RequireRole`）配合 AOP 做方法级鉴权。<br>4. **BCryptPasswordEncoder** 做密码加密存储。                                      |

### 模块 2：工单核心管理（CRUD + 列表查询）

_这是系统的“躯干”，页面上最基础的新建、列表、详情都在这里。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                                                                                                                                      |
| :--------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **动态过滤**：列表页必须有“状态”、“紧急度”、“时间范围”的组合筛选。<br>2. **数据脱敏/隔离**：列表接口必须根据当前登录角色，动态拼接不同的 SQL 查询条件。<br>3. **乐观锁防超卖（防并发误操作）**：两个人同时点“编辑”保存时，后提交的要提示“数据已被修改，请刷新”。<br>4. **逻辑删除**：删除不是真删（DELETE），而是更新 `is_deleted = 1`，保留历史痕迹。                                     |
| **核心技术点（Java技术栈）** | 1. **MyBatis-Plus** 的 `Wrapper` 构造复杂动态查询，或使用 **Spring Data JPA** 的 `Specification`。<br>2. 使用 **VO（View Object）** 接收前端参数，**DTO（Data Transfer Object）** 做内部传输，**Entity** 对应数据库，严格分层。<br>3. **分页插件**（如 PageHelper 或 MyBatis-Plus 自带分页）。<br>4. **乐观锁**：数据库表加 `version` 字段，更新时 `where id = ? and version = old_version`。 |

### 模块 3：状态机与生命周期（State Machine）⭐ _这是你的核心亮点_

_这是最值钱、面试最加分、日本客户最抠细节的地方。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                                                                                                                                              |
| :--------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **状态硬编码约束**：不允许跳跃式变更（比如“未处理”不能直接变“已完成”，必须先经过“处理中”）。<br>2. **操作按钮动态渲染**：根据当前状态和当前角色，后端接口只返回“允许执行的下一个状态列表”。例如：处于“待确认”时，前端只给用户显示“确认解决”和“重新打开”两个按钮。<br>3. **原因必填校验**：当状态变为“已拒绝”或“已关闭”时，强制要求填写“拒绝/关闭原因”。                                            |
| **核心技术点（Java技术栈）** | 1. **状态模式（State Pattern）** 或 **策略模式（Strategy Pattern）** 代替大量的 `if-else`。<br>2. 使用 **Java Enum（枚举）** 定义所有状态和允许的流转路径（例如：`OPEN` -> `IN_PROGRESS`）。<br>3. 若想更高级，引入 **Spring StateMachine** 框架，用配置文件管理状态机（便于后期日本客户改流程，不用动业务代码）。<br>4. 状态变更时记录 **操作日志（Audit Log）**：谁、什么时间、从A状态改到了B状态。 |

### 模块 4：工单协作/评论回复（Comment & Timeline）

_这就是那个“像微信聊天一样的对话流”。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                     |
| :--------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **回复即更新**：当客服在详情页回复内容时，工单状态自动从“处理中”推进到“待确认（Pending）”。<br>2. **内容过滤（XSS防御）**：防止用户输入恶意 `<script>` 标签。<br>3. **@提及功能（如果V1.0不做，可以标记为V2.0）**：输入 `@张三` 自动通知张三。                            |
| **核心技术点（Java技术栈）** | 1. **富文本编辑器**（如 UEditor 或 WangEditor）后端接收 HTML 内容，但需要做 **XSS 过滤**（用 Jsoup 库清洗标签）。<br>2. 数据库设计为**自关联**或**父子表**（`ticket_id` + `parent_comment_id`）支持楼中楼。<br>3. 使用 **Redis 缓存** 当前工单的未读回复数，减轻数据库压力。 |

### 模块 5：文件附件管理（File Upload/Download）

_对应你说的“文件上传”，但包含许多隐藏坑。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                                                           |
| :--------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **类型与大小硬限制**：前端拦截+后端拦截（防止绕过前端），只允许 `.jpg/.png/.pdf`，单文件≤5MB。<br>2. **关联绑定**：上传时必须传 `ticketId`，将附件挂在工单下；如果工单删了（逻辑删除），附件是否物理删除？建议保留。<br>3. **敏感文件水印**（V2.0）：如果是内部机密系统，下载 PDF 时自动打上“用户名+时间”水印。 |
| **核心技术点（Java技术栈）** | 1. **Spring MultipartFile** 接收文件。<br>2. **存储抽象层（接口设计）**：写 `StorageService` 接口，实现类用 **MinIO（本地开发）** 或 **阿里云 OSS/七牛云**。<br>3. 文件命名：用 **UUID + 时间戳** 重命名，防止重名覆盖。<br>4. **异步压缩（可选）**：如果用户上传超大图片，后台用 Thumbnailator 库压缩生成缩略图。 |

### 模块 6：异步通知引擎（Notification / Email）

_对应你说的“邮件通知”，但设计上要解耦，不要阻塞主流程。_

| 维度                         | 具体内容                                                                                                                                                                                                                                                                                               |
| :--------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **核心设计点（业务规则）**   | 1. **触发点策略**：只在“新建工单”、“状态变为处理中（分配）”、“有新回复”三个节点触发通知。<br>2. **防骚扰机制**：同一分钟内，同一个工单不重复给同一个人发两封邮件（用 Redis 做去重标记）。<br>3. **通知开关**：允许用户在个人设置里关闭邮件通知（需要用户表预留 `notify_flag` 字段）。                  |
| **核心技术点（Java技术栈）** | 1. **Spring Mail（JavaMailSender）** 发送 SMTP 邮件。<br>2. **异步注解 `@Async`** 开启线程池异步发送，不让用户“卡”在转圈等待邮件发送成功。<br>3. **消息队列（进阶）**：引入 **RabbitMQ** 或 **RocketMQ**，把发邮件任务丢进队列，削峰填谷。<br>4. 使用 **Thymeleaf** 模板引擎编写漂亮的 HTML 邮件模板。 |

### 🗺️ 模块依赖关系图（写架构文档必看）

在写《System Architecture Design》时，你可以画这样一个依赖流向：

> **用户请求** → **认证模块（拦截）** → **权限校验** → **业务服务层（状态机校验）** → **（异步）通知引擎** → **返回响应**

- **模块 1（权限）** 是最底层的基础，其他所有接口都依赖它。
- **模块 2（CRUD）** 和 **模块 3（状态机）** 是平级的，但状态机逻辑需要注入到 CRUD 的“更新”方法中。
- **模块 4（评论）** 会触发 **模块 3（状态变更）**，又会触发 **模块 6（通知）**。
- **模块 5（文件）** 是独立工具，挂在模块 2 和模块 4 下。
